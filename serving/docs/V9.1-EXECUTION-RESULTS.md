## Phase 2 — Cosmos regression hunt

### Phase 2b: cosmos OpenClaw lane smoke
**Result**: 38/66 (57.6%) effective, 33/66 (50.0%) first-try
**vs iter-32 baseline**: 51/66 (77.3%) → **-13 cases**
**vs the prior 27B-FP8 cosmos baseline**: 34/66 (51.5%) → +4 cases (similar level)

### Phase 2c: cosmos direct lane smoke
**Result**: 25/66 (37.9%) effective, 21/66 (31.8%) first-try
**vs Phase 2b OpenClaw**: -13 cases → direct lane **WORSE** than OpenClaw

### Phase 2d: Root cause (CONFIRMED, with evidence)

The regression is **NOT** a parser bug or template bug. The cosmos-reason2-8b model on v9 emits tool calls with **structural errors** that composer's validator catches and rejects with HTTP 400:

```
Sample 1 — missing parentName, used wrong tool entirely:
  model emitted: <function=catalog_read>... but bridge classified as tree_draft_insert_node
  composer error: "tree_draft_insert_node requires parentName"

Sample 2 — invalid sibling reference:
  args: {"node": {...}, "parentName": "return_rest"}
  composer error: "Node 'return_rest' (move_manipulator_action): allows at most 0 children"

Sample 3 — passing both parentName AND afterName/beforeName (mutually exclusive):
  args: {"afterName": "pick_graspable", "beforeName": "move_to_home", "parentName": "pick_and_place", ...}
  composer error: "do not pass parentName alongside afterName/beforeName"

Sample 4 — passing both afterName AND beforeName (forbidden):
  args: {"afterName": "pick_graspable", "beforeName": "move_to_home", ...}
  composer error: "pass at most one of afterName, beforeName"

Sample 5 — afterName references nonexistent sibling:
  args: {"afterName": "pick_graspable", ...}
  composer error: "afterName sibling not found: pick_graspable"
```

After 16 retries (BRIDGE_MAX_TURNS), the model never converges to a valid shape. The OpenClaw lane partially mitigates this via:
- Richer system prompt (cosmos sees more guidance about valid tool shapes)
- /compact mechanism providing prior-turn summaries that anchor the schema

The direct lane is starker — no compact, no system prompt richness — cosmos's bad-shape rate is higher.

### What the regression is NOT
- ❌ NOT the `nodeName` missing bug from initial hypothesis (verified: 0/16 `tree_draft_insert_node` calls in last 50 records had missing nodeName)
- ❌ NOT a parser issue (cosmos's hermes parser correctly extracted XML tool-call shape into JSON; the args structure is what's wrong)
- ❌ NOT a template issue (template applied correctly; user message reached the model intact)
- ❌ NOT a lane bug (both lanes show the same root issue; OpenClaw mitigates slightly)

### What the regression IS
- ✅ **Model-quality degradation specific to cosmos-reason2-8b on v9 image** (vLLM 0.22 + transformers 5.9 + cosmos's Qwen3-VL template combination)
- ✅ Cosmos lacks the schema-following capability needed for this composer-assistant task at this stack version

### Recommended remediations
1. **Short-term**: production-default the larger 35B-A3B-NVFP4 model (iter-3 RedHat = 51/66 = 77.3%, matches iter-32 baseline)
2. **Medium-term**: re-test cosmos with **transformers 5.7.0** (v8 pin) in a sidecar to see if downgrade restores accuracy
3. **Long-term**: cosmos-reason2-8b is fundamentally weaker at strict tool-schema following — replace it for composer workloads with 35B-A3B (or larger)
4. **Out-of-scope here but worth tracking**: NVIDIA may ship a Cosmos Reason 3 with stronger tool-following; revisit then

## Phase 4 — NVIDIA 35B-A3B-NVFP4 on v9.1

### Phase 4a/4b: load test — ✅ WORKED

PR #42124 ("Add LM head quantization support for ModelOpt", merged 2026-05-26) is **confirmed working**. NVIDIA weights load cleanly:
- All 3 shards loaded (57s main + 5s drafter)
- MTP detected, embedding + lm_head shared with drafter
- MoE backend: **MARLIN** (NVIDIA-recommended)
- NVFP4 GEMM kernel: `FlashInferFP8ScaledMMLinearKernel` for FP8 linears + Marlin for NVFP4 MoE
- Model footprint: 21.1 GiB (vs RedHat's 22.6 GiB — comparable)
- Engine init total: 243s (warmup + KV cache)

**Performance caveat**: throughput is **8.3 tok/s** on v9.1 NVIDIA path (Marlin software-dequant FP4), vs **18.9 tok/s** on v9 RedHat path (VLLM_CUTLASS native NVFP4 MoE).

vLLM logs the cause:
```
WARNING: Your GPU does not have native support for FP4 computation but FP4
quantization is being used. Weight-only FP4 compression will be used
leveraging the Marlin kernel. This may degrade performance for compute-heavy
workloads.
```

SM110a doesn't have native FP4 instructions in CUTLASS yet; Marlin synthesizes FP4 via packed-int4 → bf16 dequant. The RedHat path picks `VLLM_CUTLASS` MoE which uses a different FP4 path that IS fast on SM110.

This is consistent with the [V9-35B-A3B-NVFP4-NVIDIA-RECIPE.md](V9-35B-A3B-NVFP4-NVIDIA-RECIPE.md) observation that the iter-3 RedHat config is the better production fit on Thor — even with NVIDIA's actual weights loadable on v9.1, the Spark-recipe `--moe-backend marlin` is slower than `--moe-backend auto` (which lands on VLLM_CUTLASS for RedHat's compressed-tensors format).

## Phase 5 — Streaming tool dispatch (DEFERRED)

Implementing true SSE chunk-by-chunk passthrough requires:
- `vllm-proxy.py`: detect Content-Type=text/event-stream upstream, switch to chunked transfer; preserve full-body logging
- `manyforge_assistant_bridge/bridge.py`: flip `stream:True`, write SSE parser, reassemble tool calls from deltas
- `openclaw_assistant_bridge/adapter.py`: same (openclaw-gateway may also need streaming)
- A/B smoke validation

Today's discovery: cosmos OpenClaw lane **already streams** at vLLM level (proxy logs show SSE-format `body_raw_excerpt`). The proxy buffers the full SSE blob and forwards it as a regular HTTP response with Content-Length. Bridges parse the SSE format themselves. So we get SSE-format data, just not chunked-transfer delivery.

Estimated impact: faster time-to-first-tool-call (~5-15s lower latency on long thinking cases), zero pass-rate change. Marginal benefit relative to the implementation effort (~150-300 LoC across 3 components + risk surface around tool-call reassembly).

**Recommendation**: schedule as a future phase ("v9.2 streaming pass-through") when latency becomes the bottleneck. For now, RedHat 35B path at 19 tok/s with full-buffer is fast enough.
