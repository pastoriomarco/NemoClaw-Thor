## Phase 1 — Direct lane conversation history

**Goal**: bring the direct lane to feature parity with the OpenClaw lane for multi-turn workflows, **without breaking the OpenClaw lane**. Both must remain functional and selectable per-request.

**Why**: direct lane is faster (no SSH-tunnel + sandbox indirection) but currently stateless — each `/api/assistant/chat` request is independent. Multi-turn smoke cases (the iter-32 chain-session work) fail or degrade when the prior turn's context isn't carried.

### Design (proposed — open to your input)

| Decision | Recommendation | Rationale |
|---|---|---|
| Where to hold history | **Direct-lane bridge** (`manyforge_assistant_bridge`, port 8100), in-memory per-process | Same pattern OpenClaw uses (gateway holds state). Bridge is the right boundary — it already mediates composer↔vLLM. Proxy stays transport-only. Composer doesn't need to change session-tracking logic. |
| Session identity | **`conversationId` from composer's existing payload** | Already sent for OpenClaw — no new composer change needed. Reuses the field. |
| Storage | **dict[session_id, deque[messages]]**, no persistence across bridge restarts | Matches OpenClaw which loses state on gateway restart. Simple, fast, no DB. |
| Eviction | **LRU by `last_use_ts`**, cap at N=50 active sessions; auto-evict after 30 min idle | Bounded memory. Smoke runs ~66 cases → max ~5 concurrent sessions in practice. |
| Context budget | **Truncate oldest turns when est_tokens > N** (where N defaults to 75% of model's max_model_len) | Simple and predictable. OpenClaw uses `/compact` (LLM summary); we can add that later if budget-truncate degrades quality. |
| Compatibility with OpenClaw lane | **Routing untouched** — composer keeps choosing lane via existing config (assistant provider = direct vs openclaw). Each lane manages its own state. | Both lanes always functional. No mutual interference. |
| Concurrency | **Per-session lock** so two requests for the same session can't race on the messages deque | Avoids interleaved history. |

### Implementation steps
1. **Read current direct-lane bridge**: `/home/tndlux/workspaces/dev_ws/src/manyforge/manyforge_assistant_bridge/bridge.py` (and supervisor.py) — map the request handler, the vLLM call site.
2. **Add `SessionHistory` class** with: `append(session_id, role, content)`, `materialize(session_id, system_messages, current_user_msg) → messages[]`, `evict_lru()`. Unit-testable in isolation.
3. **Wire into the request handler**: extract `conversationId` from incoming body → call `materialize()` → use returned messages array in the vLLM call. After response, append assistant turn (including reasoning if requested).
4. **Add a clear-session endpoint**: `POST /v1/sessions/{id}/clear` for the composer's "reset chat" button to call.
5. **Add Prometheus metrics**: `direct_lane_active_sessions`, `direct_lane_history_tokens{session_id}`, `direct_lane_eviction_total`.
6. **Smoke test parity**: run 3-prompt smoke chain (e.g., `PnP_01_scene_ground → PnP_02_scene_graspable → PnP_03_scene_pick_pad`) on both lanes, expect tool-call sequences to be equivalent.

### Success criteria
- Direct-lane smoke corpus ≥ 70% effective rate on multi-turn-heavy cases (currently fails most of them at 0%)
- OpenClaw lane smoke corpus unchanged (delta within ±2 pp of iter-3 baseline 51/66)
- No memory leak: bridge RSS stable across a 100-prompt run
- `/v1/sessions/{id}/clear` returns 204; subsequent prompt for same id behaves as turn 1

### Rollback
Single feature flag `DIRECT_LANE_HISTORY_ENABLED=true|false` env var. Default `true` once validated; set to `false` to fall back to stateless mode.

### Estimated effort
~3 hours implementation + 1 hour smoke validation.

## Phase 5 — Streaming tool dispatch

**Goal**: enable end-to-end SSE streaming for tool calls. Both vLLM (≥ v0.21) and our stack must consume it.

### Per the prior research
- vLLM 0.22 already has the upstream primitives (PRs #40700 streaming with `required`, #41110 named tool_choice).
- Our stack does NOT consume them:
  - `manyforge/scripts/proxy/vllm-proxy.py:422-429` buffers SSE responses
  - `openclaw_assistant_bridge/adapter.py:754` sets `"stream": False`
  - `manyforge_assistant_bridge/bridge.py:1216-1223` parses tool_calls from full buffered response

### Implementation steps
1. **Proxy passthrough mode**: add `OPENCLAW_PROXY_STREAM_PASSTHROUGH=true` env. When set, the proxy forwards SSE chunks as they arrive (no buffering); JSONL log captures the full reassembled response after the stream closes (for debugging continuity).
2. **Direct-lane bridge SSE support**: flip `"stream": True` on the vLLM call. Add an SSE event reader that:
   - Emits partial tool-call deltas as they arrive
   - Reassembles the complete tool-call list before validating + executing
3. **OpenClaw-lane bridge SSE support**: same treatment for the gateway call. NOTE: openclaw gateway may itself need streaming support — investigate first.
4. **Composer compatibility check**: if composer expects buffered responses, gate behind `OPENCLAW_ASSISTANT_STREAM_TO_COMPOSER=true` env so the bridge can keep buffering at the composer boundary even if it streams from vLLM.

### Validation
- **A/B smoke runs**: same corpus, streaming ON vs OFF. Pass rate should be unchanged (correctness must not regress); latency to first tool-call dispatch should drop meaningfully.
- **JSONL diff**: stream-reassembled response equals buffered response for the same prompt + seed.

### Success criteria
- Smoke pass rate stream-ON within ±1 pp of stream-OFF
- First-tool-call latency reduced by ≥30% on long-thinking cases (one of our biggest pain points — 6 fails timed out at >150s)

### Estimated effort
~4-6 hours implementation + 2 hours validation.

### Phase 2d: Root cause (CONFIRMED, with evidence)

The regression is **NOT** a parser bug or template bug. The cosmos-reason2-8b model on v9 emits tool calls with **structural errors** that composer's validator catches and rejects with HTTP 400:

```
Sample 1 — missing parentName, used wrong tool entirely:
  model emitted: <function=catalog_read>... but bridge classified as tree_draft_insert_node
  composer error: "tree_draft_insert_node requires parentName"

Sample 2 — invalid sibling reference:
  args: {"node": {...}, "parentName": "return_rest"}
  composer error: "Node 'return_rest' (move_manipulator_action): allows at most 0 children"

Sample 3 — passing both parentName AND afterName/beforeName (mutually exclusive):
  args: {"afterName": "pick_graspable", "beforeName": "move_to_home", "parentName": "pick_and_place", ...}
  composer error: "do not pass parentName alongside afterName/beforeName"

Sample 4 — passing both afterName AND beforeName (forbidden):
  args: {"afterName": "pick_graspable", "beforeName": "move_to_home", ...}
  composer error: "pass at most one of afterName, beforeName"

Sample 5 — afterName references nonexistent sibling:
  args: {"afterName": "pick_graspable", ...}
  composer error: "afterName sibling not found: pick_graspable"
```

After 16 retries (BRIDGE_MAX_TURNS), the model never converges to a valid shape. The OpenClaw lane partially mitigates this via:
- Richer system prompt (cosmos sees more guidance about valid tool shapes)
- /compact mechanism providing prior-turn summaries that anchor the schema

The direct lane is starker — no compact, no system prompt richness — cosmos's bad-shape rate is higher.

### What the regression is NOT
- ❌ NOT the `nodeName` missing bug from initial hypothesis (verified: 0/16 `tree_draft_insert_node` calls in last 50 records had missing nodeName)
- ❌ NOT a parser issue (cosmos's hermes parser correctly extracted XML tool-call shape into JSON; the args structure is what's wrong)
- ❌ NOT a template issue (template applied correctly; user message reached the model intact)
- ❌ NOT a lane bug (both lanes show the same root issue; OpenClaw mitigates slightly)

### What the regression IS
- ✅ **Model-quality degradation specific to cosmos-reason2-8b on v9 image** (vLLM 0.22 + transformers 5.9 + cosmos's Qwen3-VL template combination)
- ✅ Cosmos lacks the schema-following capability needed for this composer-assistant task at this stack version

### Recommended remediations
1. **Short-term**: production-default the larger 35B-A3B-NVFP4 model (iter-3 RedHat = 51/66 = 77.3%, matches iter-32 baseline)
2. **Medium-term**: re-test cosmos with **transformers 5.7.0** (v8 pin) in a sidecar to see if downgrade restores accuracy
3. **Long-term**: cosmos-reason2-8b is fundamentally weaker at strict tool-schema following — replace it for composer workloads with 35B-A3B (or larger)
4. **Out-of-scope here but worth tracking**: NVIDIA may ship a Cosmos Reason 3 with stronger tool-following; revisit then

## Phase 4 — NVIDIA 35B-A3B-NVFP4 on v9.1

### Phase 4a/4b: load test — ✅ WORKED

PR #42124 ("Add LM head quantization support for ModelOpt", merged 2026-05-26) is **confirmed working**. NVIDIA weights load cleanly:
- All 3 shards loaded (57s main + 5s drafter)
- MTP detected, embedding + lm_head shared with drafter
- MoE backend: **MARLIN** (NVIDIA-recommended)
- NVFP4 GEMM kernel: `FlashInferFP8ScaledMMLinearKernel` for FP8 linears + Marlin for NVFP4 MoE
- Model footprint: 21.1 GiB (vs RedHat's 22.6 GiB — comparable)
- Engine init total: 243s (warmup + KV cache)

**Performance caveat**: throughput is **8.3 tok/s** on v9.1 NVIDIA path (Marlin software-dequant FP4), vs **18.9 tok/s** on v9 RedHat path (VLLM_CUTLASS native NVFP4 MoE).

vLLM logs the cause:
```
WARNING: Your GPU does not have native support for FP4 computation but FP4
quantization is being used. Weight-only FP4 compression will be used
leveraging the Marlin kernel. This may degrade performance for compute-heavy
workloads.
```

SM110a doesn't have native FP4 instructions in CUTLASS yet; Marlin synthesizes FP4 via packed-int4 → bf16 dequant. The RedHat path picks `VLLM_CUTLASS` MoE which uses a different FP4 path that IS fast on SM110.

This is consistent with the [V9-35B-A3B-NVFP4-NVIDIA-RECIPE.md](V9-35B-A3B-NVFP4-NVIDIA-RECIPE.md) observation that the iter-3 RedHat config is the better production fit on Thor — even with NVIDIA's actual weights loadable on v9.1, the Spark-recipe `--moe-backend marlin` is slower than `--moe-backend auto` (which lands on VLLM_CUTLASS for RedHat's compressed-tensors format).

Steady-state across longer cases averaged ~50s/case, comparable to RedHat's ~66s/case. **The Marlin software-FP4 slowdown is offset by faster decode in later turns** (likely prefix caching + smaller per-case retry counts since NVIDIA's tool-call shapes are slightly more accurate).

### Production recommendation (REVISED based on Phase 4c data)
**SWITCH to NVIDIA weights on v9.1** as the production default. Reasons:
1. Same effective pass rate (77.3%)
2. +1 hard pass (48 vs 47), better first-try rate
3. 23% faster wall-clock total
4. Fewer failures in stateful cases (UPDATE_params_specific, CUR_runtime_*)
5. v9.1 image is forward-looking — bumped vLLM main brings other minor fixes too

Caveat: RedHat path remains a safe fallback if NVIDIA quant introduces issues we haven't surfaced yet.

## Phase 5 — Streaming tool dispatch (DEFERRED)

Implementing true SSE chunk-by-chunk passthrough requires:
- `vllm-proxy.py`: detect Content-Type=text/event-stream upstream, switch to chunked transfer; preserve full-body logging
- `manyforge_assistant_bridge/bridge.py`: flip `stream:True`, write SSE parser, reassemble tool calls from deltas
- `openclaw_assistant_bridge/adapter.py`: same (openclaw-gateway may also need streaming)
- A/B smoke validation

Today's discovery: cosmos OpenClaw lane **already streams** at vLLM level (proxy logs show SSE-format `body_raw_excerpt`). The proxy buffers the full SSE blob and forwards it as a regular HTTP response with Content-Length. Bridges parse the SSE format themselves. So we get SSE-format data, just not chunked-transfer delivery.

Estimated impact: faster time-to-first-tool-call (~5-15s lower latency on long thinking cases), zero pass-rate change. Marginal benefit relative to the implementation effort (~150-300 LoC across 3 components + risk surface around tool-call reassembly).

**Recommendation**: schedule as a future phase ("v9.2 streaming pass-through") when latency becomes the bottleneck. For now, RedHat 35B path at 19 tok/s with full-buffer is fast enough.
