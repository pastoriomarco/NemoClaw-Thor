## Task 1 — Unlock faster FP4 kernels on Thor (SM110a)

### TL;DR
**Thor has working FP4 hardware** (verified 875 TF dense FP4 at sm_110a via CUTLASS C++).
The blocker is **CUTLASS DSL `admissible_archs` lists** that gate FP4 paths to sm_100a/103a/120a/121a — NOT sm_110a. Patching that allowlist (mirror of the DGX Spark sm_121 community patch in cutlass#3096) should unlock 30-40 tok/s on the NVFP4 35B-A3B path vs current 8 tok/s (Marlin software dequant) or 19 tok/s (VLLM_CUTLASS, partial native).

### Confirmed hardware
- NVIDIA Jetson Thor blog: 2070 TF sparse / 1035 TF dense FP4
- Forum user verified 875 TF (84% of spec) with `-DCUTLASS_NVCC_ARCHS=110a` on CUDA 13.1+
- NVIDIA staff (AastaLLL) confirmed: "Thor is Blackwell, has instruction support for mxfp4, can run NVFP4"
- `tcgen05.mma.kind::mxf4/nvf4` works on sm_110a (must use `sm_110a` not bare `sm_110`)

### Arch-gating status
| Path | sm_110a | Notes |
|---|---|---|
| CUTLASS C++ (`-DCUTLASS_NVCC_ARCHS=110a`) | ✅ WORKS | 875 TF achieved by community |
| CUTLASS DSL (`BlockScaledMmaOp`) | ❌ BLOCKED | Gated to sm_100a/103a/120a/121a only |
| FlashInfer `mm_fp4` CUTLASS backend | ✅ probably IN at C++ | Arch list reportedly [100,103,110,120,121]; docs narrate only 120 |
| FlashInfer `mm_fp4` b12x/TRT-LLM/cuDNN | ❌ BLOCKED | Gated `major==12` |
| FlashInfer MoE FP4 (`VLLM_USE_FLASHINFER_MOE_FP4=1`) | ❌ broken on Thor | Forced to set =0 |
| QuTLASS | ❌ BLOCKED | README: sm_100a/sm_120a only |
| vLLM Marlin (weight-only FP4) | works (software) | What we use; ~8 tok/s on NVIDIA weights |
| VLLM_CUTLASS NVFP4 MoE | partial native | What RedHat path uses; ~19 tok/s — current Thor best |
| TRT-LLM FP4 (TensorRT 10.13) | ❌ silent fallback | NVIDIA tensorrt#4590, unfixed |

### Action plan (for a future v9.2 image)
1. **Patch CUTLASS DSL `admissible_archs`** to add `Arch.sm_110a`. Single-list edit in `python/CuTeDSL/cutlass/cute/nvgpu/tcgen05/mma.py` + ~5 sibling files. Mirror of cutlass#3096 (DGX Spark sm_121 community patch). Realistic upside on 35B-A3B: **19 → 30-40 tok/s**.
2. **Patch QuTLASS `CUDA_ARCHS`** to add `11.0a` and rebuild.
3. **Apply pytorch#172807 fix** — `TORCH_CUDA_ARCH_LIST=11.0a` must be set explicitly; auto-detect strips the `a` suffix and kills NVFP4.
4. Re-test NVIDIA 35B + Spark recipe on patched stack; expect 2x throughput improvement (catching up to and exceeding the RedHat 19 tok/s baseline).

## Task 2 — Cosmos regression remediation

### Root cause analysis (from 265 cosmos chat-completion records in proxy JSONL)
The cosmos-reason2-8b v9 regression (38/66 vs iter-32 baseline 51/66) has **two distinct symptoms**:

1. **30.2% narration mode** (80/265 records) — model emits prose like "Done. Added X node to the sequence" with **zero tool calls**. The model believes it performed the action.
2. **47% missing `nodeName`** (54/115 tree_draft_insert_node calls) — model knows the right tool but omits a required arg. This is the original hypothesis confirmed.

Only 2/115 mutex violations — not the dominant issue.

### Remediation experiment
Used `OPENCLAW_PROXY_USER_MESSAGE_SUFFIX` (existing mechanism in vllm-proxy.py) to append a directive to every user message:

```
REMINDER: For action requests (add/insert/wrap/move/delete/update/replace),
ALWAYS call the appropriate tool first — do NOT just describe the action as
already done. When calling tree_draft_insert_node, ALWAYS include `nodeName`
(a unique string id for the new node) as a top-level argument alongside
`parentName` or `afterName`/`beforeName`. Use AT MOST ONE of `parentName`,
`afterName`, `beforeName` per call.
```

### If remediation works on subset
Roll out to full corpus, document as production env. Likely worth keeping the suffix on permanently for cosmos workloads.

### If remediation doesn't help
Cosmos is fundamentally weaker at strict schema-following on v9. Options:
- Test with transformers 5.7 / 5.8 downgrade in sidecar to confirm transformers-driven regression
- Switch composer-assistant model permanently to 35B-A3B (already production default)

## Task 3 — Direct lane conversation history retest (DONE CORRECTLY)

### Why the original test was insufficient
The smoke runner gives **each case a unique `conversationId`** → SessionHistory is rebuilt empty per case → history feature never exercised. The original Phase 2c smoke (25/66 direct lane) tested lane base behavior, not the history feature.

### Correct A/B test
- **Skip OpenClaw lane** — it has its own chain-session + /compact mechanism; comparing to it muddles the question
- **Compare Direct + history ON vs Direct + history OFF** on a 3-turn chain with shared conversationId
- **Verify mechanically via proxy capture** what messages array vLLM actually received

### Test
3-turn chain (model: NVIDIA Qwen3.6-35B-A3B-NVFP4 on v9.1):
- T1: "My favorite color is teal and my favorite number is 42. Confirm you noted these."
- T2: "What is my favorite color and number?"
- T3: "What number did I tell you?"

### Results
| Turn | HISTORY ON response | HISTORY OFF response |
|---|---|---|
| T1 | "noted teal and 42" | "noted teal and 42" |
| T2 | **"color: teal, number: 42"** ✓ | "I don't know your favorite color or number" ✗ |
| T3 | **"42"** ✓ | (control validated by T2 already) |

### Mechanical proof via proxy capture
**HISTORY ON** — messages array sent to vLLM per turn:
```
TURN 1: [user]                                       (1 msg)
TURN 2: [user, assistant, user]                      (3 msgs — history injected)
TURN 3: [user, assistant, user, assistant, user]     (5 msgs — full chain)
```

**HISTORY OFF** — messages array sent to vLLM per turn:
```
TURN 1: [user]   (1 msg)
TURN 2: [user]   (1 msg — NO history)
```

### Verdict
- ✅ SessionHistory mechanism works correctly
- ✅ Bridge correctly prepends prior turns when ENABLED
- ✅ Bridge correctly skips prepending when DISABLED
- ✅ Model behavior matches (recalls with history, can't without)
- 📝 Feature applies to genuine multi-turn user interactions, not the smoke corpus runner pattern (which keeps cases isolated by design)
