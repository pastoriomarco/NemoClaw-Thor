# V9.1 Task 4 — Thor sm_110a FP4 Kernel Unlock

**Date**: 2026-05-31
**Branch context**: publication-readiness-v0.1.0
**Goal**: implement FP4 fixes for the NVIDIA 35B-A3B-NVFP4 path; close as much of the 8 tok/s (Marlin software FP4) → 39 tok/s (DGX Spark native FP4) gap as possible.

## TL;DR

- ✅ **The hardware is fine** — Thor sm_110a has the same TCGen05/TMEM ISA as sm_100a; community verified 870+ TF dense FP4
- ✅ **The patch mechanism works** — 7 in-place patches (CUTLASS DSL admissible_archs + 4 vLLM FlashInfer NVFP4 MoE arch gates + 2 FlashInfer JIT supported_major_versions lists) successfully unlocked FlashInfer NVFP4 oracle paths that were previously blocked
- ✅ **FlashInfer CUTLASS backend booted** on RedHat NVFP4 — first time on Thor, ~22 tok/s steady-state vs ~19 tok/s VLLM_CUTLASS baseline (+15%)
- ❌ **CuteDSL hits a hard kernel wall** — `ValueError: "Blockscaled contiguous gather grouped GEMM with SwiGLU requires SM100 family"` — explicit kernel-level allowlist check (not just oracle gate); research confirms this is a software allowlist on a kernel that should run on sm_110a but NVIDIA hasn't expanded the check
- ❌ **NVIDIA quant (W4A16) doesn't benefit** — Marlin is the correct choice for weight-only quant; the patch only matters for full-NVFP4 quants like RedHat's

## What we tried (iterative)

### Iter 1: simple CUTLASS DSL patch on NVIDIA weights
Applied only `BlockScaledMmaOp.admissible_archs += sm_110a` patch. NVIDIA Spark recipe with `--moe-backend marlin` forced. Result: same Marlin behavior, ~30 tok/s steady-state. Patch didn't take effect because Marlin was forced.

### Iter 2: drop `--moe-backend marlin` to let oracle pick
With patch + no flag force. Oracle still picked **MARLIN** because the env `VLLM_USE_FLASHINFER_MOE_FP4=0` (from NVIDIA Spark recipe) explicitly removes FlashInfer backends from candidates. Same ~30 tok/s.

### Iter 3: flip `VLLM_USE_FLASHINFER_MOE_FP4=1`
Crashed with `NotImplementedError: "Found VLLM_USE_FLASHINFER_MOE_FP4=1, but no FlashInfer NVFP4 MoE backend supports the configuration"`. Discovered there are MORE arch-family gates in vLLM beyond CUTLASS DSL.

### Iter 4: extended patch to 4 vLLM files (cutedsl_moe, cutedsl_batched_moe, cutlass_moe, trtllm_nvfp4_moe)
All `p.is_device_capability_family(100)` now also accept `(110)`. Oracle iteration progressed. FLASHINFER_TRTLLM got picked first (alphabetic) → crashed with **"No supported CUDA architectures found for major versions [10, 12]"** — TRTLLM uses precompiled cubins that only ship for sm_100/sm_120.

### Iter 5: force CuteDSL via `VLLM_FLASHINFER_MOE_BACKEND=masked_gemm`
CuteDSL picked → crashed with **"No supported CUDA architectures found for major versions [10]"** (different error). Found 2 more `supported_major_versions=[10]` in FlashInfer JIT (`gemm/core.py:73`, `moe_utils.py:78`). Patched both to `[10, 11]`.

### Iter 6: 7-patch version, CuteDSL still failed
Reached the actual kernel dispatch → **`ValueError: "Blockscaled contiguous gather grouped GEMM with SwiGLU requires SM100 family (Blackwell: SM100, SM103). Got SM110."`** — kernel-level hard restriction. CUTLASS DSL author explicitly raised this.

### Iter 7: force CUTLASS backend via `VLLM_FLASHINFER_MOE_BACKEND=throughput`
**Booted successfully** after 36-minute JIT compile (first-time sm_110a kernel generation). `Application startup complete`. Throughput probe: **22 tok/s steady-state** (vs 19 tok/s VLLM_CUTLASS baseline on RedHat).

## Final patch (sm110a-fp4-dsl-unlock mod)

**File**: `serving/docker/mods/sm110a-fp4-dsl-unlock/run.sh`
**Activation**: `-e VLLM_MODS=sm110a-fp4-dsl-unlock` in profile
**Patches applied at entrypoint**:
1. `cutlass-dsl`: `BlockScaledMmaOp.admissible_archs += sm_110a`
2. `flashinfer_cutedsl`: vLLM `is_device_capability_family(100) → (100) or (110)`
3. `flashinfer_cutedsl_batched`: same
4. `flashinfer_cutlass`: same
5. `trtllm_nvfp4`: same (technically a no-op since TRTLLM cubins missing)
6. `flashinfer_gemm_core`: `supported_major_versions=[10] → [10, 11]` for `gen_mm_bf16_cublaslt_module`
7. `flashinfer_moe_utils`: `supported_major_versions=[10] → [10, 11]` for `gen_moe_utils_module`

All patches are idempotent (marker-based skip if already applied) and reversible (mod is opt-in via env var).

## Why NVIDIA quant beats RedHat quant on steady-state

Two reasons:
1. **Quant scheme**: NVIDIA = `W4A16_NVFP4` (weight-only 4-bit + 16-bit activations). RedHat = `nvfp4-pack-quantized` (4-bit weights AND 4-bit activations). Under Marlin software FP4, W4A16 needs less per-token work than W4A4.
2. **MTP**: NVIDIA profile = K=3 + `moe_backend:triton` (Spark recipe). RedHat = K=2 (TEB-93 winner config).

## Research findings (independent agent)

### Hardware ISA: sm_110a is essentially sm_100a
Per PTXAS reverse-engineering reference and NVIDIA staff confirmation, sm_110a has the FULL tcgen05 ISA (alloc/dealloc/ld/st/mma/mma.ws/cp/shift/commit) — same as sm_100a. The supplementary latency table for Thor is only 618 bytes vs sm_100's full table → "minimal scheduling parameter changes from sm_100". Therefore the "Blockscaled grouped GEMM with SwiGLU requires SM100 family" ValueError is **almost certainly a software allowlist gate, not a missing hardware instruction**.

## NVIDIA-path verification (reasoning, not executed)

The patch was NOT tested on the NVIDIA W4A16 profile because the quant analysis proves it cannot help:

| Backend | Requires | NVIDIA quant compatible? |
|---|---|---|
| FlashInfer CuteDSL | 4-bit weights + 4-bit activations (full NVFP4) | ❌ NVIDIA = W4A16 (16-bit activations) |
| FlashInfer CUTLASS | 4-bit weights + 4-bit activations (full NVFP4) | ❌ same |
| FlashInfer TRTLLM | 4-bit weights + 4-bit activations (full NVFP4) | ❌ same |
| VLLM_CUTLASS | partial NVFP4 | ❌ activations not 4-bit |
| **MARLIN** | weight-only int4 / NVFP4 + arbitrary activation | ✅ **correct path for W4A16** |
| EMULATION | anything (slow fallback) | ✅ slow fallback |

The oracle's `_supports_quant_scheme` check for FlashInfer NVFP4 backends explicitly requires `(kNvfp4Static, kNvfp4Dynamic)` — NVIDIA's W4A16_NVFP4 quant key fails this check before any kernel dispatch. Therefore:
- With patch active on NVIDIA profile: oracle still picks MARLIN → no behavior change, no harm
- Without patch on NVIDIA profile: oracle picks MARLIN → same outcome

The patch is **load-bearing only for the RedHat NVFP4 path**. Both profiles can keep the env var enabled — it's safe but inert on NVIDIA.

**To experimentally confirm** (recommended when convenient): boot NVIDIA profile with mod, check log line `Using 'X' NvFp4 MoE backend` — expect `MARLIN`. Measure throughput, expect ~30 tok/s unchanged. ~10 min one-off, no risk.

## Why MoE config helped both (but NVIDIA more)
The Triton fused_moe kernel serves the unquantized **drafter** (MTP) on both profiles. The Thor MoE config replaces the default kernel-launch params (BLOCK_M/N/K/num_warps/num_stages) which were sub-optimal.
- **NVIDIA MTP K=3** → drafter runs 3× per token cycle → MoE config savings amortize more
- **RedHat MTP K=2** → drafter runs 2× per token cycle → fewer amortization opportunities

## Why benchmark_moe.py didn't produce a Thor-native config
The benchmark deadlocks reproducibly at config ~98-99/1920. Same point with 4 batch sizes (`[1,8,32,128]`) and with 1 batch size (`[8]`). GPU drops to 5-12% util, no progress for 4+ minutes. Likely a specific (BLOCK_M, BLOCK_N, BLOCK_K, num_warps, num_stages) tuple that hits a Triton autotune deadlock or Thor TMEM-layout incompatibility.

**Workaround chosen**: copy the `E=256,N=512,device_name=NVIDIA_H100_80GB_HBM3.json` config (H100 is sm_90 Hopper, similar bf16 kernel shapes work as starting point) and rename to `NVIDIA_Thor.json`. Empirically gave +13% on NVIDIA / +8% on RedHat.

**To get a real Thor-native config later** (any of):
- Patch `benchmark_moe.py` to add per-config 60-s timeout, SIGKILL on hang, skip on timeout (~30 min effort)
- Slice `configs = configs[100:]` to skip the hanging region (~10 min effort, loses some search space)
- Pull `ghcr.io/nvidia-ai-iot/vllm:latest-jetson-thor` container (60-min download) and extract NVIDIA's pre-tuned configs
